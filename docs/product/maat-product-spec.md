>
> 最后更新：2026-10-12
>

## 1. 已确认的产品定位

### PROD-001：主要用户

主要用户是使用 Pi Agent 的人。用户希望在安装 Maat Pi Extension 后，
通过自然语言让 Pi 操作手机，完成自己想要的任务。

这是本轮 MVP 的首要用户场景，而不是以 App 开发、调试或自动化测试为首要场景。
该优先级不意味着删除已有开发相关能力或改变 Core 的宿主中立边界。

### PROD-002：主要使用入口

主要入口是 Pi 中的 Maat Extension。用户向 Pi 描述目标，Pi 借助 Maat
观察和操作手机上的现有 App。

“安装后直接使用”是期望的用户体验；必要的环境准备、设备选择、
权限授权及人工操作的具体流程和验收标准尚待确认。
本项不表示已经实现免配置，也不构成删除其他入口的决定。

### PROD-003：任务场景

用户已给出的代表性任务：

- 在 X 上查找内容。
- 使用微信回复一个人的消息。

这些例子用于明确产品方向；首轮验收范围见 PROD-005。
搜索目标、目标联系人、回复内容、授权方式及结果确认规则需要在具体任务中明确。
本次需求讨论不构成对真实设备发送消息、登录或其他副作用操作的授权。

### PROD-004：Android 与 iOS 同级交付

本轮 MVP 同时以 Android 和 iOS 为必达平台，不将其中一端仅作为后续扩展。
首轮核心任务见 PROD-005，必须在两平台分别通过完整用户路径验收，
两边均通过才算双平台目标完成。

共同的任务目标和成功标准保持一致，允许环境准备、平台实现和 App 界面存在差异。
同级交付不要求同时修改两套实现，也不意味着所有平台或 App 功能完全对等。

验收通过真实 Pi Agent 和 Maat Extension，在两平台各自的受支持物理机上进行。
已有实现、自动化测试和脚本驱动的设备验证可作为基础，
但不能替代本轮已确认用户任务的双平台验收。
单端通过不能代表另一端通过；某端受环境阻塞时，明确记录该端尚未完成。

### PROD-005：首轮任务为 App 内内容查找与整理

用户已确认首轮采用以下组合，不要求两个平台使用同一个 App：

- Android：在 X 上搜索指定主题，阅读相关帖子，整理结果。
- iOS：在微信“搜一搜”搜索指定主题，阅读相关文章，整理结果。

两端都通过 Pi 和 Maat 在指定手机的 App 内完成查找与阅读，
返回基于实际读到内容的结果和可核对的来源；不得改用网页或模型记忆代替手机操作。
无法找到或访问内容、需要登录时如实说明，不编造结果。
首轮不发送消息、发布内容、点赞或关注。

用户已确认主题为“AI 编程助手的使用经验”，每个平台实际打开阅读 3 条相关内容，
逐条整理主要观点，并提供作者、帖子或文章标题等可核对的来源。
两端无需找到相同内容；不足 3 条不能算任务通过，也不得用搜索结果标题代替实际阅读。
首轮复用现有电脑、Pi、Maat Extension 和已安装且已登录的 App，
由 Pi 检查准备情况、建立或复用连接，再完成任务；不重装、不清数据。
解锁、认证等本人步骤如实记录，耗时、尝试次数和人工介入作为观测指标，
首轮不设置时间或尝试次数的通过门槛。
该起点不代表全新机器安装即用已经通过，
详见 [内容查找验收 Spec](../specs/mobile/content-search.md)。
微信回复仍为代表性目标场景，不属于本轮验收任务。

### PROD-006：每个手机连接生命周期重新选择目标

MVP 不保存用户级、工作区级或项目级的设备绑定，也不提供“默认设备”或
“记住此设备”。每个新的 Mobile Session／手机连接生命周期都根据当时的
discovery 事实选择目标：

- 没有符合条件的候选时，不创建 Session、不执行准备副作用或手机操作，并明确说明阻塞。
- 恰有一个候选时，可以为本次生命周期选择它，但必须在首次准备副作用、
  Session 创建或手机操作前清楚披露目标摘要及“当前只有一个候选”的原因。
- 有多个候选时，必须由用户根据当前事实明确选择；用户在当前请求中给出的描述
  如果只能对应一个候选，也可作为明确选择。显示名不是身份，不能仅凭名称相似、
  排序、最近使用或历史配置猜测。

候选编号或引用只属于一次短期发现结果，不是设备身份，也不得持久化。
收到选择后，必须在全局 device operation slot 内重新验证它仍唯一对应当前候选，
再固定精确 `DeviceIdentity + endpoint`。选择被固定并由该生命周期接纳时，
生命周期开始；其 active lifetime 包括准备、Session 创建与健康复用、readiness、
人工接管等待、同一目标上的恢复，直到成功 `release`／`close`。

active 生命周期始终固定同一精确 identity 与 endpoint。设备缺失、断线或 endpoint
变化时，只能恢复原 identity 和原 endpoint；不得 fallback、静默 remap、选择剩余设备
或开始新的选择。若原目标无法恢复，fail closed 并报告。可能已进入 Worker 的动作
仍按“可能已经执行”处理，绝不因恢复而自动重放。

成功 `release`／`close` 后立即忘记该目标，后续生命周期重新 discovery 和选择；
仅模型 turn 结束不等于生命周期结束。release／close 失败或结果不确定时，不得声称
已经关闭或忘记；可以保留最小的进程内 safety/cleanup 状态以阻止误操作，但它不是
可供继续操作或下次选择复用的设备绑定。进程或宿主重启后不恢复、不迁移、不收养
旧选择或旧 Session，也不从磁盘读取选择；MVP 不把目标选择写入磁盘。

旧 `{kind, name}` 等 Session hints 仅是兼容输入，不是持久选择、用户同意或动作授权。
它们只有在与当前事实精确且无歧义匹配时，才可缩小本次向用户提出的候选方案；
不能在多候选时替用户确认，不能形成下一生命周期的目标，也不得迁移到
`BindingStore`。选择目标只回答“本次连接操作哪台设备”，不授权安装、重签、重启、
认证、发送等动作，不证明设备 ready、动作完成或用户业务成功。

“记住此设备”是未来可选能力，不属于 MVP。

## 2. 待确认的产品范围

- 首次安装到手机可操作的准备流程、前提条件和体验指标。
- 只读任务与发送等副作用任务的授权和确认方式。
- 设备锁定、认证和动作结果不确定时的用户流程。
- 当前 MVP 的范围、非目标以及其他平台和入口的兼容要求。

未决事项不能由当前实现、技术设计或 Agent 推定为已批准需求。
